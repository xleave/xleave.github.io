最近在一台新 Windows 机器上配置开发环境，过程远比预期曲折。硬件是新的，系统是干净的，但”干净”在这里意味着所有默认开启的安全机制都在、没有任何历史配置、网络环境也不通。

这篇记录五个坑。我刻意写清了每个坑我最初的判断是什么、为什么错——因为复盘下来，那些误判比最终结论更有参考价值。

1. TLS 吊销检查离线，而不是网络不通

症状：curl 下载 GitHub 文件，握手阶段直接失败。winget install Git.Git 报 InternetOpenUrl() failed / 0x80072efd。Invoke-WebRequest 报”基础连接已经关闭：发送时发生错误”。

最初的判断：GitHub 被墙了，需要换镜像源。

实际：报错里的关键词被我忽略了——

schannel: next InitializeSecurityContext failed:
CRYPT_E_REVOCATION_OFFLINE (0x80092013)

这是证书吊销检查失败：系统连不上 CRL/OCSP 服务器（企业网络、安全软件接管证书链、或代理环境下常见），于是 schannel 拒绝完成握手。跟”能不能连上目标站点”是两件事。

解决：

# curl：跳过吊销检查
curl.exe -L --ssl-no-revoke -o out.zip <url>

# git：换 schannel 后端并关闭吊销检查
git config --global http.sslBackend schannel
git config --global http.schannelCheckRevoke false

教训：网络类报错先读完整错误串。CRYPT_E_REVOCATION_OFFLINE 和 Could not resolve host、Connection timed out 是完全不同的病因，前者的”不通”发生在 TLS 层之上，换镜像源也没用。

2. 直连失败其实是”没走代理”

症状：git ls-remote https://github.com/cli/cli.git 报：

Failed to connect to github.com:443 after 21076 ms: Could not connect to server

但同一台机器上浏览器能正常访问 GitHub。

误判过程：我先后怀疑过 DNS（解析正常，能拿到正常的 A 记录）、防火墙、SSL 后端配置，甚至一度以为是第 3 节那个策略在拦。逐项排除后才发现矛盾点：

浏览器能上、命令行不能上——这个差异本身就指向代理：浏览器走系统代理（HKCU:\...\Internet Settings 里的 ProxyServer），而 git / gh 默认不读系统代理，只认 http.proxy 配置或 HTTP(S)_PROXY 环境变量。

查出代理端口：

Get-NetTCPConnection -State Listen |
  Where-Object { $_.LocalAddress -eq '127.0.0.1' } |
  Select-Object LocalPort, OwningProcess

Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings' |
  Select-Object ProxyEnable, ProxyServer

解决（git 只需配置一次，写进它自己的 .gitconfig，不碰系统环境）：

git config --global http.proxy  http://127.0.0.1:7897
git config --global https.proxy http://127.0.0.1:7897

教训：“浏览器能上、命令行不能上”几乎等于”代理没配”。另外我倾向于把代理写在工具自己的配置文件里，而不是全局环境变量——前者作用域明确、一条命令可撤，后者会影响所有程序且容易被遗忘。

3. Smart App Control：一个会拦掉所有原生模块的策略

症状：sharp、rollup 等含原生 .node 的文件加载失败：

ERR_DLOPEN_FAILED: An Application Control policy has blocked this file.

同时系统弹窗提示”此应用的一部分已被阻止……无法确认谁发布了 xxx.dll”。

我连续误判了两次，这是本篇最该记的部分。

第一次误判：我查到这是 Smart App Control（SAC），又搜到”关闭 SAC 需要重装系统”，于是告诉用户”这个只能重装解决”。

第二次误判：用户关掉杀毒软件后无效，我进一步查证，修正为”可以关闭，但关闭后无法再开启，是单向开关”。

真相：用户实际测试后反馈——可以自由开关。我复核了注册表，VerifiedAndReputablePolicyState 确实从 1 变成了 0，且原生模块随即全部加载成功：

VerifiedAndReputablePolicyState = 0
sharp:              加载成功 ✓
rollup 原生绑定:     加载成功 ✓

我错在哪：两次判断都建立在”搜到的说法”上，而没有把它当作待验证假设去实测。第一次连”能否关闭”都没查证就下了重装结论；第二次查到了单向后，也没有让用户实测就当成定论。

这个策略的性质：SAC 属于代码完整性策略，与杀毒软件是两套机制。所以换杀软、关 Defender 都不会影响它——它拦的是”未签名/无信誉的二进制”，且拦截发生在加载时，跟文件是否存在、来源是否可信无关。

排查入口：

Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\CI\Policy' |
  Select-Object VerifiedAndReputablePolicyState
# 0 = 关闭 / 1 = 强制开启 / 2 = 评估模式

教训：把”查到的说法”降级为假设，能用一行命令验证的就先验证。我对这个策略连着错了两次，都是同一个毛病——相信检索结果多于相信眼前这台机器。

4. 用 WASM 版替代原生绑定

在策略尚未解除时，我找到了一条不用改系统的绕行路径：把 rollup 换成官方 WASM 实现 @rollup/wasm-node。它是纯 WASM，没有原生 .node 绑定，因此策略无从拦截。

关键在于 pnpm 的 overrides 支持 npm 别名语法：

# pnpm-workspace.yaml
overrides:
  rollup: npm:@rollup/wasm-node@4.64.0

版本号对齐很重要——rollup 4.64.0 对应 @rollup/wasm-node 4.64.0，避免 API 漂移。

这条路的成本：WASM 版性能低于原生版，且与 CI 走的不是同一条路径（CI 在 Ubuntu 上用原生版）。所以策略解除后我就把它撤掉了，恢复原生——本地验证与线上构建应尽量同构，否则”本地过了”就没有保证意义。

附带一个容易踩的坑：pnpm 用符号链接 + 严格依赖树布局，顶层 node_modules 里找不到 rollup 是正常的（未声明为直接依赖）。不要因为 require('rollup') 报 MODULE_NOT_FOUND 就以为装漏了——真正该跑的是 astro build 本身。

5. 生成物的所有权：一个自造的”假故障”

症状：build-check 报 3 个徽章文件缺失，但对应文章明明存在。

我的错误假设：先怀疑行尾。生成器用 /^---([\s\S]+?)---/ 解析 frontmatter，若文件是 CRLF 则 ---\r\n 可能匹配不上，导致文章被静默跳过。这个假设看起来很合理，但实测推翻了它——49 篇文章的 frontmatter 全部匹配成功（其中 48 篇是 CRLF，1 篇是 LF，正则都能处理）。

真因：是我自己的操作顺序造成的状态不一致。

构建链里 generate-badges.mjs 会遍历所有文章、生成对应 SVG，然后删除任何”没有对应文章”的徽章文件。也就是说，public/badges/ 是生成物的领地，由这个脚本拥有。

而我此前用 git checkout -- public/badges 把它还原成了只有 46 个已跟踪文件的状态，随后跳过生成步骤直接构建——于是页面里引用了尚未生成的徽章：

期望徽章 49 个 / 磁盘实际 46 个 / 缺失 3 个

按正确顺序（先生成、再构建）重跑后：

A) generate-badges 后 = 49 个
B) compress-images 后 = 49 个
C) 审计：缺 0、多 0     ← 完全一致

教训：当一个目录是生成物时，不要去”还原”它——还原会制造出一个脚本预期之外的状态。要么让它由生成器全权管理，要么在还原后先跑生成器再构建。另外，我最初怀疑的”CRLF 导致正则失配”虽然在这台机器上不成立，但对只按 \n 处理行尾的脚本来说是真实风险，值得在自己写解析时注意。

汇总

#症状真因处理
1curl/winget 握手失败，0x80072efdCRYPT_E_REVOCATION_OFFLINE：吊销服务器不可达curl --ssl-no-revoke；git 关 schannelCheckRevoke
2git 连不上 443，浏览器正常命令行工具不读系统代理给 git 配 http.proxy（写在 .gitconfig，不塞环境变量）
3An Application Control policy has blocked this fileSmart App Control 拦截未签名原生模块确认 VerifiedAndReputablePolicyState 状态；关杀软无效
4无法加载原生绑定同上临时用 @rollup/wasm-node 别名顶替（版本对齐）
5构建报徽章缺失手动还原生成物目录造成状态不一致让生成器拥有该目录；还原后必须先跑生成

一点反思

这五个坑里，技术含量最高的可能是第 4 个（WASM 别名顶替），但真正值得记的是第 3 个——我在同一个问题上错了两次，两次都是”查到说法 → 直接下结论”，跳过了”在这台机器上验证”这一步。

工具链排错有个特点：症状相似但病因完全不同。握手失败可能是网络、可能是代理、也可能是代码完整性策略；“找不到模块”可能是没装、可能是布局差异、也可能是被策略拦截。真正区分它们的不是经验，而是读完整错误串 + 做最小验证实验。

还有一件事值得单独说：关于生成物目录，我踩的坑本质上是自治边界问题——一处目录被脚本 A 拥有，就不该手动改它再指望脚本 B 行为正常。这类问题在构建链里很常见，而且报错信息通常指向错误的方向（它报”文件缺失”，而问题在于”我不该动那个目录”）。
